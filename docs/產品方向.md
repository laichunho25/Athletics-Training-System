# ATM 產品方向與介面守則

> 這份文件記錄 ATM「要做什麼、不做什麼」，以及介面上的取捨原則。
> 規格書（資料模型、欄位）見 [../ATM_SPEC.md](../ATM_SPEC.md)，這份只談方向。
> 最後更新：2026-09-12

---

## 一、三個功能方向

系統只服務三件事。任何新功能先問：它屬於哪一項？三項都不屬於，就不做。

### (A) 安排、紀錄、管理

幫教練與運動員把**訓練、傷患、營養**三塊日常事務放進同一個地方。

| 範疇 | 對應模組 | 核心動作 |
|---|---|---|
| 訓練 | `planning` / `training` / `programs` | 排週期、排課表、登錄每一組的目標與完成值 |
| 傷患 | `injury` | 傷患日誌、痛感追蹤、替代動作 |
| 營養 | `nutrition` | TDEE、營養素、睡眠與恢復 |

> 判準：這一頁能不能讓人**在三十秒內把今天發生的事登進去**。做不到就是設計失敗。

### (B) 從紀錄做出跨範疇分析

紀錄本身沒有價值，**把不同範疇的數字擺在同一條時間軸上比**才有價值。

- 單一範疇的趨勢：某個動作的重量、某個項目的成績、體重與體脂
- 跨範疇的關聯：
  - 體組成 × 重量訓練 —— 同樣的 100kg 深蹲，70kg 和 85kg 的人不是同一件事
  - 訓練負荷 × 傷患 —— ACWR、Monotony、Strain 與痛感紀錄對照
  - 動作重量 × 肌肉脂肪比例 × 訓練時間 —— 三面向擺同一列
- 產出：看得懂的結論句（「相對力量 +6%」「建議 ±10% 以內」），不是一堆原始數字

> 判準：教練看完這一段，**能不能改下一週的課表**。不能，就是圖表太多、結論太少。

### (C) 融合工具與平台，收在一個清晰的系統裡

- 已接：Cloudflare R2 影片儲存、影片分析（逐格／標線）、體測數據 OCR、公開報名頁、雙語（中／英）
- 原則：外部工具接進來之後，**在 ATM 裡只留一個入口**，不讓使用者在兩套介面之間切換

> 判準：新接一個工具，介面上**只能多出一個入口**，不能多出一層選單。

## 二、介面守則（為什麼要一直刪東西）

使用者是教練與中學運動員，不是資料分析師。介面複雜度是這個系統最大的風險。

### 守則

1. **一個概念只有一個名字。** 同一件事在側欄、頁面標題、說明文字裡必須用同一個詞。
2. **標題只寫名詞，解釋寫在別處。** 側欄項目最多四個字；長的解釋放 tooltip。
3. **每加一個設定，先問誰會改它。** 沒有人會改第二次的設定就是多餘的裝飾。
4. **長頁面要有導航。** 超過三段的頁面必須有段落導航列，讓人先看目錄再決定看哪一段。
5. **收合狀態要記住。** 使用者關掉的段落，下次回來還是關著的。

### 已移除的多餘設定（2026-09-12）

| 移除的東西 | 原因 |
|---|---|
| 頂欄「LIVE + 時鐘」 | 純裝飾。作業系統已經有時鐘，而且「LIVE」暗示有即時連線，實際上沒有 |
| 頂欄「表格間距」下拉（緊湊／標準／寬鬆） | 三選一的排版偏好，沒有人會改第二次；CSS 的 `data-density` 保留備用 |
| 數據分析頁「全部收起／全部展開」旁的一長串說明 | 按鈕本身已經自明，說明文字佔掉一整行 |

### 已統一的字眼

| 原本 | 現在 | 說明 |
|---|---|---|
| 運動練習項目庫 / 訓練活動庫 | **動作庫** | 同一個模組出現過兩個名字 |
| 運動員列表 | **運動員名單** | 「列表」是程式用語 |
| 全隊燈號總覽 | **全隊總覽** | 「燈號」是實作細節 |
| 運動員狀態總覽 | **狀態總覽** | 側欄群組已經叫「運動員」，不用再寫一次 |

> 最嚴重的一處：教練那一頁（`/team/`）的 `<h1>` 原本寫著「運動員狀態總覽」，
> 但側欄與麵包屑叫它「全隊燈號總覽」——**同一頁兩個名字**。現在統一為「全隊總覽」。

### 英文介面

`locale/en` 的守門測試（`core/test_i18n_catalogue.py`）要求每一句都要有翻譯、不准留 fuzzy。
這次一併把影片額度／進階會員那一批 56 句補齊，英文介面不再夾雜中文。

## 三、數據分析頁的段落導航（揭書式）

分析頁是全系統最長的一頁（六個大段）。六段同時攤在一個版面上，光是捲就會嚇跑人。
所以這一頁不是一張長紙，而是一本書：**一次只顯示一段**，頂上的導航列就是書籤。

- 只列出這個範疇實際有資料的段落，沒資料的段不出現
- 按書籤就揭到那一段，其餘的段收起來不佔版面
- 版面底下有「← 上一部份 ／ 第幾部份 ／ 下一部份 →」，不想用書籤就逐頁翻
- 記住這個範疇最後看的是哪一段：換項目、換週數而重新載入時回到原處
- 網址的 `#錨點` 最大：從別頁連過來（例如營養頁連 `#bodygoal`）直接落在那一段
- 沒有 JS 的時候不進入揭書模式，六段整頁攤開，照樣讀得到
- 導航列右邊保留「全部收起／全部展開」，管的是段落裡面那些卡片

段落順序固定（由近到遠：先看原始紀錄，再看分析，最後看跨範疇）：

```
紀錄 → 項目分析 → 比賽 → 訓練負荷 → 體組成 → 多面向
```

實作：[`static/js/secnav.js`](../static/js/secnav.js)；`.secnav` / `.anabook` / `.anapanel`
樣式在 `static/css/atm.css`。每一段是一個 `<section class="anapanel" id="錨點"
data-sec="標題">`，全部包在 `<div class="anabook">` 裡。藏著的框量不到寬高，
圖表會畫成 0×0，所以揭到一頁就叫該頁的 Chart 重新 `resize()` 一次——
與 [`static/js/fold.js`](../static/js/fold.js) 展開卡片時做的事是同一招。

## 四、手機上的登錄與版面

運動員真正登錄的地方是場邊，不是書桌：一隻手拿著手機、一隻手打。
所以「在手機上登得完一堂課」是這個系統的及格線，不是加分項。

判斷準則：**這一頁在 375px 寬的螢幕上，能不能一隻手打完？**

- **鍵盤不要跳**：iOS 只要輸入框小於 16px 就自動放大整頁。表格裡那些窄格
  （組數、重量、次數）以前沒蓋到，等於每打一格畫面跳一次——窄螢幕下
  所有輸入框一律 16px。
- **鍵盤要對**：數字格直接跳數字鍵盤。step 是整數（組、次）給純數字，
  其餘（重量、秒數）給有小數點那一款。
- **點了就能打**：手機上點進一格會把原本的數字整個選起來，直接打新的蓋過去，
  不用先按五下刪除。桌機不這樣做——用滑鼠點通常是要改中間某一位。
- **按得中**：觸控裝置上會按的東西一律留到 40px。
- **知道自己在哪一列**：欄位多的表格在手機上是橫向捲的，第一欄（組號／日期）
  與表頭固定不動，捲到第五欄也知道自己在改哪一組。
- **常用的鍵不要在頁尾**：數據分析的揭頁鍵在手機上黏在畫面底，讀到哪裡都按得到。
- **滾輪不要改到數字**：桌機滑鼠捲過表格時，停在數字格上會把值捲掉，這裡直接擋掉。

實作：[`static/js/numpad.js`](../static/js/numpad.js)（鍵盤與選取，全站載入）、
`static/css/atm.css` 最後一段「手機：登錄時的輸入，與窄螢幕的看法」。
