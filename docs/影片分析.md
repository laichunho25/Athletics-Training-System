## 一、結論先講

**分兩期做，第一期不碰 AI。**

- **第一期**：純影片平台——上傳、影片庫、播放器（變速／逐格）、教練在時間點留批註、並排比較。這已經是 Hudl、OnForm 這類專業教練平台的核心功能，本身就是完整可用的產品。
- **第二期**：在第一期累積的影片上加姿態估計（pose estimation），算出真實的關節角度與時間序列，再交給 Claude 寫成教練語言的回饋。

**為什麼先做第一期**：如果教練用一個學期後發現手動逐格看片加批註已經夠用（很常見的結果），第二期的月費與約一千行程式碼就省下來了；如果教練說「我想要膝角數字」，那時已經有一整個學期的真實影片可以驗證第二期做得準不準。

## 二、已排除的方案：抽格丟給 Claude

最初評估的做法是「影片 → ffmpeg 抽 12–16 張關鍵格 → 當成多張圖送 Claude 分析」。

**已排除。** 原因有二：

1. 產品觀感上不夠專業。
2. 成本反而更高——16 張圖約 25k input tokens（每條約 US$0.12），而第二期送「關節角度數字」只要約 2k tokens（每條約 US$0.03）。

**但要記住這個事實**：沒有任何 LLM API 吃原始影片，Messages API 只接受圖片（jpeg/png/webp/gif）與 PDF，沒有 video 這種 content block。市面上所有「AI 影片分析」產品底層都是抽格。所以「不抽格」等於「不用 LLM 直接看動作」，這正是第二期改走 pose estimation 的理由——它不是抽格的簡化版，而是更專業的版本。

## 三、第一期：純影片平台

### 3.1 三個必須解決的技術問題

#### （1）檔案放哪——不能放 Render 容器

`render.yaml` 目前是 `plan: starter` 且**沒有掛 disk**，容器檔案系統每次部署就重置。

| | Render Disk | 物件儲存（Cloudflare R2） |
|---|---|---|
| 改動 | 掛 disk + 設 `DJANGO_MEDIA_ROOT` | 加 `django-storages` + `boto3`，改 `config/settings.py` 的 `STORAGES` |
| 儲存費 | 約 US$0.25/GB/月 | 約 US$0.015/GB/月 |
| 流量費 | 含在服務內 | **$0（R2 不收 egress）** |
| 代價 | 服務鎖死單一 instance、失去 zero-downtime deploy | 多一個外部服務要管 |

**決定：用 Cloudflare R2。** 它 S3 相容，`STORAGES` 換個 backend 即可；`MEDIA_ROOT` 那幾行留著給本機開發。影片每次播放都是 egress，R2 免流量費是關鍵。

#### （2）上傳不能走 gunicorn

`render.yaml` 的 `startCommand` 是 `--timeout 120`。一條 100MB 的片經 Django 上傳會超時，而且整個檔案會佔住 worker 記憶體。

**做法：前端直傳。** Django 只發一個 presigned PUT URL → 瀏覽器用 `fetch` 把片直接送去 R2 → 成功後才 POST 一筆 metadata 回 Django。這樣 gunicorn 永遠只處理幾 KB 的 JSON。

#### （3）格式相容性——這個一定會咬到

iPhone 預設拍 HEVC 的 `.mov`，Chrome / Android 播不了。三個選項：

- 瀏覽器端先轉碼成 H.264 MP4（免費，吃學生手機效能）← **先用這個**
- 上傳頁明確要求學生改用「最相容」拍攝設定（免費，但靠自律）
- 後端排隊跑 ffmpeg 轉檔（Render background worker 約 US$7/月）

這是最容易被忽略、上線後最多人投訴的一點。

### 3.6 分析工具與放大（2026-09-10 追加）

全部在瀏覽器裡完成，量出來的東西按「加入分析重點紀錄」寫進 `VideoNote`，
運動員自己打開就看得到教練量了什麼、劃了什麼，不用另外傳圖。

| 工具 | 做什麼 | 存進 `data` 的內容 |
|---|---|---|
| 計時 | 標 A、標 B（或按 A / B 鍵），量中間那一段；填了距離就一併算平均速度 | `{"kind": "timing", "distance_m": 30}`，區間本身存在 `at_sec` / `end_sec` |
| 數步 | 腳落地按一下（空白鍵），算步數、步頻、每步平均 | `{"kind": "steps", "taps": [...]}` |
| 放大 | ＋／−／還原（鍵盤 + - 0），按著 Ctrl 滾滾輪或觸控板捏合以游標為中心縮放；放大後拖曳可移動畫面 | 不存，純看片用 |
| 劃線 | 疊在影片上的 canvas：直線、三點量角度、水平線、垂直線、手繪 | `{"kind": "draw", "shapes": [{"t": "line", "p": [[x, y], ...]}]}` |

兩個要注意的地方：

- **準確度受格率限制。** 30fps 一格 0.033 秒，逐格只能停在格上，所以量出來的
  時間誤差約在正負一格之內。要量觸地時間這種等級的東西，得用手機的慢動作
  （120 / 240fps）拍，並在播放列的「格率」選對——那個選項只是告訴前端一格多久，
  不會改變影片本身。
- **座標一律存 0～1 的比例，不是像素。** 同一條線在手機、電腦、不同解析度的影片上
  才會畫在同一個位置。`data` 整包是前端送上來的，等於使用者可以隨便塞，
  所以 `video/services.py` 的 `_clean_data` / `_clean_shape` 會把形狀種類、座標範圍、
  筆數（400 步 / 60 個形狀 / 一筆 300 點）、NaN 與 inf 全部擋掉再存。

`data` 用一個 JSONField 而不是拆成好幾欄，是為了第二期：關節角度、
桿路那些數字可以直接放進同一個欄位，不用再開一次 migration。

刻意不做的事：後端 ffmpeg 轉檔（HEVC 改用前端偵測＋提醒使用者改設定）、
任何 AI 分析（那是第二期）。

### 3.7 上線流程（2026-09-10 實際做過一次）

換機器、換 bucket、或哪天要重來一次的話，照這個順序：

1. **Cloudflare → R2 → 開一個 bucket**（正式站用的那個）。
2. **R2 → Manage API Tokens → Create API Token**，權限要選
   **Object Read & Write**（只給 Read 的話上傳會失敗，`check_r2` 會講）。
   記下 Access Key ID 與 Secret Access Key，Secret 只會顯示一次。
3. **Render → 你的 service → Environment**，加四個變數：
   `R2_BUCKET`、`R2_ACCOUNT_ID`、`R2_ACCESS_KEY_ID`、`R2_SECRET_ACCESS_KEY`。
   （`R2_ENDPOINT` 與 `R2_PUBLIC_BASE` 可留空；沒設 public base 就用簽發的
   6 小時 presigned GET 播放。）
   **貼的時候不要多按 Enter**——原因見 3.8。
4. **R2 → bucket → Settings → CORS Policy**，貼上（網址換成你自己的）：

   ```json
   [
     {
       "AllowedOrigins": ["https://www.hohosports.com", "https://hohosports.com"],
       "AllowedMethods": ["PUT", "GET", "HEAD"],
       "AllowedHeaders": ["content-type"],
       "MaxAgeSeconds": 3600
     }
   ]
   ```

   這一步漏掉的話，前端直傳會 100% 失敗而且錯誤訊息很不明顯。
   用 onrender.com 的網址測就要把那個網域也加進去。
5. **部署**。`build.sh` 裡已經有 `migrate --no-input`，migration 會自己跑，
   不用手動進 shell。
6. **驗收**：Render → Shell → `python manage.py check_r2`。
   它會依序檢查連線、寫入、刪除、CORS，每一步都印結果。

設定沒設齊時整套會自動退回本機 `MEDIA_ROOT` 的一般表單上傳，
所以本機開發不必開 Cloudflare 帳號。

### 3.8 上線時踩到的坑（都修好了，但值得記住）

| 症狀 | 真正的原因 | 怎麼查出來的 |
|---|---|---|
| 「上傳失敗：連不上雲端儲存。」 | bucket 根本沒設 CORS | 從外面對 R2 endpoint 送一個 `curl -X OPTIONS`，回 `403 CORS not configured` |
| CORS 修好之後改成 `Server Error (500)` | `R2_ACCESS_KEY_ID` 的值裡夾了一個換行（在 Render 貼的時候多按了 Enter）。金鑰要算進 AWS4 簽章，帶著換行 Python 的 `http.client` 直接拒發整個請求，錯誤訊息是 `Invalid header value`，完全看不出是空白字元 | Render Shell 裡跑 `default_storage.save()` 一行，拿到完整 traceback |
| 上面那個坑為什麼躲過了 `check_r2` | `video/storage.py` 讀環境變數時有 `strip()`，`config/settings.py` 沒有。**同一份設定有兩個讀法**，所以簽發網址與自我檢查都正常，只有 django-storages 那條路壞掉 | 兩邊都改成 `_r2_env()` 統一 strip，`check_r2` 也加了空白字元的警告 |
| 伺服器端 500MB 上限形同虛設 | `video_sign` 讀 `request.POST["size"]`，但前端送的欄位叫 `size_bytes` | 寫測試時發現 |
| `video_detail` 未登入也進得去 | 新加的 helper 放在 `@login_required` 和 view 中間，把那個 decorator 接走了 | 測試 client 打過去炸在 `'str' object has no attribute 'user'` |
| 測試報 `Missing staticfiles manifest entry` | `ManifestStaticFilesStorage`：新的 js/css 要先 `collectstatic` | 改前端後記得 `py -3.13 manage.py collectstatic --noinput` |
| `purge_videos` 的測試無故失敗 | 保留期限是拿**真的今天**算的，測試卻用固定的 `TODAY = 2026-06-01` | 測試改用 `timezone.localdate()` |

兩個環境上的提醒：

- 這台機器要用 **`py -3.13 manage.py ...`**，直接打 `python` 的那個沒裝 Django。
- 改 management command 之後跑一次 `py -3.13 -m py_compile`。
  `manage.py check` **不會**載入 command，語法錯誤它抓不到，測試也一樣過。

## 四、第二期：姿態估計 + AI 回饋

### 4.1 做法

用 MediaPipe 或 MoveNet 逐格算骨架關鍵點 → 得到每一格的關節座標 → 導出真實指標（膝角、髖角、槓路軌跡、步頻、觸地時間、左右對稱性）→ 把**數字**（不是圖）交給 Claude 寫成教練語言的回饋。

輸出是骨架疊加影片 + 時間序列曲線 + 文字回饋。這才是專業器材在做的事。

### 4.2 在哪裡跑推論

| | 瀏覽器端（MediaPipe JS） | 後端 |
|---|---|---|
| 成本 | **$0** | Render standard worker 約 US$25/月 |
| 速度 | 現代手機跑 30 秒片只要幾秒 | 30 秒片約需 1–3 分鐘 CPU |
| 影片傳輸 | 不用來回傳 | 要 |
| 缺點 | 結果受裝置影響 | 貴、慢 |

**建議走瀏覽器端。** Render starter 的 CPU 跑逐格推論會很吃力。

### 4.3 技術風險

MediaPipe 吐出來的是座標，**把座標轉成有意義的運動指標本身就是一門學問**，調準確度會反覆很多次。這是第二期真正的難點，不是串接 API。

### 4.4 分析品質的期望值

- **重量訓練**：判斷「深蹲膝內扣、硬舉圓背、槓路偏移、深度不足」這類，可用性不錯。
- **跑步**：定性描述（觸地位置、軀幹前傾、擺臂）OK；步頻、觸地時間這種數字**必須**靠 pose estimation 才算得準。

**務實原則：AI 出定性回饋 + 教練覆核，不要對外宣稱是量測。**

| 6 條 | 300 MB | 30 GB | 20 GB | $0.30 |
| **12 條** | **600 MB** | **60 GB** | **50 GB** | **$0.75** |
| 20 條 | 1 GB | 100 GB | 90 GB | $1.35 |

**結論：真正的「零成本」只做得到每人 2 條，那等於影片庫不能用。**
所以額度的目的不是省錢（就算全隊塞爆也只是每月一杯咖啡），而是讓佔用量
**可預測**——沒有上限的話，一條沒人會再看的 500MB 廢片乘以一百個人，
就是一筆沒人看得見、也沒人負責的帳。

定下來的預設值（後台「影片額度設定」隨時可改，不必重新部署）：

| | 條數 | 容量 | 保留天數 |
|---|---|---|---|
| 免費 | 12 | 600 MB | 90 |
| 進階會員 | 60 | 3 GB | 365 |

三個配套決定：

1. **條數與容量兩道閘都要過。** 只卡條數是個漏洞：單檔上限乘以條數才是真正
   的佔用量。12 條 × 舊的 500MB 單檔上限＝一個人 6GB，一百人就是 500GB／
   每月 $7.4。容量才是帳單看的東西，條數只是給人看的友善單位。
2. **單檔上限由 500MB 降到 150MB**（`video.models.MAX_UPLOAD_BYTES`）。
   1080p 每分鐘約 100–130MB，150MB ≈ 一分半；拿來分析的片本來就只有
   十幾二十秒。不放寬是因為容量額度用位元組算——一條五分鐘的廢片會吃掉
   整個月的額度。
3. **額度算「現在存著的片」，不是累計上傳。** 刪一條即刻還一格，
   `purge_videos` 到期清片也自動還。這樣「刪片騰空間」對運動員才是成立的，
   也不用另外記一本累計帳。

## 六、私隱與保留政策

這是 DBS 學生的影片，保留期限與存取權限遲早要向學校交代，**不如一開始就設計進去**：

- 免費 90 天後自動刪除、進階會員 365 天，教練標記為「範本」的永久保留
- 存取權限：運動員只看得到自己的片；教練看得到自己帶的運動員
- 上傳前需要家長／學生同意的流程（待確認學校要求）

保留政策同時解決成本與私隱兩個問題。

**現況**：`is_keeper`（範本）、`purge_videos`、以及 `render.yaml` 裡的 cron
都做好了，**但那條 cron 要你在 Render Dashboard 按一次 Apply 才會生效**
（Blueprint 改了不會自動建新服務）。在那之前仍然是手動跑：

```
python manage.py purge_videos           # 只列出會刪什麼（天數跟著每個人的方案走）
python manage.py purge_videos --apply   # 真的刪
python manage.py purge_videos --days 180 --apply   # 不理方案，一律用這個天數
```

天數現在讀後台「影片額度設定」那一頁（免費 90／進階 365，填 0 ＝ 不清），
`--days` 只是覆寫用的後門。清掉的片會同時還回上傳額度。

**上線步驟**：Render Dashboard → Blueprints → 這個 repo → Apply →
會多出一個 `atm-purge-videos` 的 Cron Job（約 $1/月）→ 進去 Environment
把四把 R2 金鑰與 `DJANGO_SECRET_KEY` 填上（`sync: false` 的不會從 repo 帶過去）
→ Manual Run 跑一次確認輸出。

排程是每週一香港時間 04:00（cron 寫的是 UTC 的 `0 20 * * 0`）。保留期是 90 天，
每天跑跟每週跑沒有分別，週跑反而少了「哪天誤刪要查 log」的機會。

**金鑰一把都不能少。** 少了的話 `video/storage.py` 會靜靜地退回本機檔案系統：
資料庫那行刪掉了，R2 上的物件卻留下來變孤兒——帳單照計，而且沒有任何地方看得見。

> 為什麼不省這 $1 改用「免費外部 cron 打一個秘密網址」：月費已經 $13，
> 為省 $1 去開一個能觸發刪除的公開端點，是拿攻擊面換一杯水。
